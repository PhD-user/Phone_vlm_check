# Инструкция по подготовке данных и обучению

## Что именно обучается

Визуальный энкодер MobileCLIP2-S0 уже предобучен на изображениях и текстах.
Команда extract переводит каждую фотографию в 512 чисел. Команда train обучает
по этим числам небольшую линейную голову, разделяющую Android и iPhone.
Это перенос обучения с замороженной VLM, а не обучение VLM с нуля.

Базовые веса включены. Фотографий телефонов и обученной на них головы пока нет.
GPU ускоряет extract; train работает на CPU даже при наличии видеокарты.
Дообучение слоёв нейросети в этой версии не реализовано. Для первой проверки
600 фотографий такой подход проще воспроизвести и проанализировать.

## 1 Установите окружение

Следуйте README. Проверьте `python -m phone_vlm doctor` и убедитесь, что
`base_available` равно true, `embedding_shape` равно `[1, 512]`, а версии
основных библиотек соответствуют requirements.txt. CUDA нужна только при
явном использовании GPU. Значение false допустимо для обучения на CPU.

Команды далее выполняются из корня проекта в созданном окружении.

## 2 Подготовьте фотографии

Папки:

| Путь | Что положить |
|---|---|
| `data/raw/android/` | Фотографии подтверждённых Android-смартфонов |
| `data/raw/iphone/` | Фотографии подтверждённых Apple iPhone |

Допустимы JPEG/PNG. Минимум: короткая сторона 480, длинная 640 пикселей;
максимум: любая сторона 6000. Портретная ориентация разрешена. Исходники не
растягивайте ради разрешения; увеличение маленькой картинки не добавляет деталей.
Один телефон занимает основную часть кадра. Начальная область применения:
без чехла, сильного перекрытия, сильного размытия и экстремального освещения.

По возможности снимайте заднюю панель или ракурс, где видны отличия корпуса.
Если нужны снимки спереди, включите их в ОБА класса и отдельно оцените этот
ракурс. Чёрный экран и похожие рамки часто не дают достаточной информации.

Рекомендуется хотя бы 15–20 разных физических телефонов на класс, больше
независимых устройств полезнее множества почти одинаковых кадров одного.
Это рекомендация по разнообразию, а не гарантия метрики. Android должен
включать разные бренды, поколения и конфигурации камер. У обоих классов должны
встречаться похожие фоны, освещение, качество камеры и доля предмета в кадре.
Не допускайте правила «все iPhone на белом фоне, все Android на столе».

Не используйте имена файлов и EXIF как признаки класса. Предобработка кода
читает пиксели; таблица путей служит только для выбора файлов и отчёта.

## 3 Создайте и заполните CSV

```bash
python -m phone_vlm index
```

Появится `data/labels.csv`. Откройте его как UTF-8 CSV с разделителем запятая.
В русской версии Excel удобно выбрать импорт «Из текста/CSV». Следите, чтобы
Excel не превратил идентификаторы в даты и не поменял разделитель на точку с запятой.
Пример заполнения находится в `data/labels.example.csv` и не является реальными данными.

| Поле | Как заполнить |
|---|---|
| `path` | Путь внутри проекта, например `data/raw/iphone/img_001.jpg` |
| `label` | Только `android` или `iphone`; подтверждается человеком |
| `device_id` | Один уникальный ID на физический аппарат, например `iphone_device_001` |
| `session_id` | Один ID на серию съёмки; одинаковый фон/сцена/серия должны быть связаны |
| `group_id` | Необязательная дополнительная связь: исходный интернет-снимок и его варианты |
| `phone_model` | Модель устройства, например `iPhone 13` или `Samsung Galaxy S22` |
| `source` | Собственная съёмка или источник и сведения о допустимости использования |
| `split` | Пока оставить пустым |
| `sha256`, `dhash` | Пока оставить пустыми; заполняет audit |

ID глобальны в пределах всего набора. Не используйте `device_1` для разных
аппаратов. Если один телефон снят в двух сериях, device_id сохраняется.
Если в одной серии несколько телефонов, у них общий session_id. Код объединяет
такие связи транзитивно и размещает всю связанную группу в одной части.

Если физический аппарат интернет-фото неизвестен, честно зафиксируйте это в
source. Объедините все найденные копии одного исходника через group_id. Не
утверждайте, что тест проверяет новые физические аппараты, если установить их
идентичность нельзя. Для более строгой проверки новых моделей устройств можно
в group_id поставить одинаковый идентификатор всем кадрам одной phone_model.

## 4 Проверьте изображения и дубли

```bash
python -m phone_vlm audit
```

Создаются `data/audited.csv` и `data/audited.audit.json`. Непрочитанный файл,
недопустимый формат или конфликт одинаковых файлов с разными метками останавливает
проверку. Исправьте источник/разметку и повторите. Удалять фотографии код не будет.

В JSON перечислены пары с похожим 64-битным dHash. Просмотрите их вручную:
это подсказки, а не доказательство дублирования. Обрезки, повороты и наложения
текста могут не обнаружиться. У подтверждённых вариантов одного исходника
задайте одинаковый group_id. Непохожие устройства ошибочно объединять не надо.

После исправления labels.csv создайте НОВЫЙ результат аудита:

```bash
python -m phone_vlm audit --output data/audited_v2.csv
python -m phone_vlm split --manifest data/audited_v2.csv
```

Старый результат не перезаписывается. В дальнейших примерах предполагается,
что итоговый файл разбиения называется `data/splits.csv`.

## 5 Создайте и проверьте разбиение

```bash
python -m phone_vlm split
```

Если весь набор — 300+300 снимков, цели на КАЖДЫЙ класс: train 160, val 40,
test 100. Групповое разбиение может дать другие числа, потому что делить один
аппарат между частями нельзя. В `data/splits.summary.json` проверьте реальные
числа, наличие обоих классов, количество групп и `meets_original_test_size`.

Если test имеет меньше 100 кадров любого класса, требование исходного ТЗ по
размеру теста не выполнено. Добавьте независимые данные либо заранее измените
методику. Допускается выбрать другие доли ДО обучения, ориентируясь на состав:

```bash
python -m phone_vlm split --output data/splits_v2.csv --ratios 0.50 0.15 0.35
```

При другом имени разбиения измените `manifest` в отдельной копии config.json.
Нельзя перебирать разбиения по точности модели. Разрешается выравнивать состав
и размеры до обучения по понятным правилам, сохраняя все версии и причины.

Сделайте ручную проверку нескольких групп и похожих кадров между частями.
Не редактируйте изображения после фиксации разбиения: хеши это обнаружат.
Если 600 снимков предназначены именно для train, соберите val/test дополнительно
и согласуйте новое разбиение. Простое 80/10/10 исходное требование test≥200 не выполняет.

## 6 Извлеките признаки

```bash
python -m phone_vlm extract --device auto
# Либо явно:
python -m phone_vlm extract --device cuda
python -m phone_vlm extract --device cpu --output artifacts/features_cpu.npz
```

Создаётся кэш из config, по умолчанию `artifacts/features.npz`. Для альтернативного
имени измените также `features` в конфигурации перед train. Одновременный запуск
нескольких extract в один выходной файл не поддерживается.

В кэш входят замороженные признаки всех частей; обучение использует только
train, подбор C — только val. Наличие тестовых признаков в кэше не означает,
что энкодер или классификатор на них обучаются. Обработка детерминирована,
аугментаций в первой версии нет. При сравнении CPU/GPU допустимы небольшие
численные различия. Для сопоставимых экспериментов используйте один кэш.

Если GPU сообщает out of memory, снизьте batch_size в новой конфигурации
с 16 до 8 или 4, затем извлеките признаки заново. На CPU можно оставить 16.

## 7 Обучите классификатор

```bash
python -m phone_vlm train --run runs/experiment_001
```

Проверяются значения C из `[0.01, 0.1, 1, 10, 100]`, solver lbfgs,
max_iter 3000, L2-регуляризация, class_weight balanced, seed 42.
Меньшее C означает более сильную регуляризацию. При равной val balanced
accuracy предпочтение получает меньший val log_loss, затем меньшее C.

В папке эксперимента:

| Файл | Назначение |
|---|---|
| `head.npz` | Веса линейной головы, читаются без pickle |
| `run.json` | Классы, версия, хеши, порог, предобработка и сведения об обучении |
| `training_metrics.json` | Метрики val по каждому C; тестовых метрик нет |
| `dataset_snapshot.csv` | Точная версия разметки и разбиения |
| `config_snapshot.json` | Копия конфигурации обучения |

Это уже обученная система при наличии базы из models/base. Голова сама по
себе не работает без энкодера. После выбора C голова остаётся обученной только
на train: val не добавляется в обучение задним числом.

Не удаляйте неудачные эксперименты. Фиксируйте цель и одно существенное изменение
за эксперимент. Для новых данных используйте новые имена CSV и кэша.

```bash
python -m phone_vlm --config config_experiment_002.json extract
python -m phone_vlm --config config_experiment_002.json train --run runs/experiment_002
```

Создайте копию конфигурации самостоятельно. Путь --config задаётся ПЕРЕД командой.
Относительные пути считаются от папки этой конфигурации; храните её в корне проекта.

## 8 Проведите итоговый тест

До тестирования зафиксируйте данные, модель, порог и версии. Затем:

```bash
python -m phone_vlm evaluate --run runs/experiment_001 --split test --output reports/test_001
```

Получите accuracy, balanced accuracy, precision/recall/F1 по классам, матрицу
ошибок, log_loss, Brier score, ECE и долю ответов выше порога. В матрице строки —
истинный класс, столбцы — предсказанный; порядок android, iphone. Ошибки ответов
с низкой уверенностью тоже входят в основные метрики.

`classification_passed` проверяет test, минимум 100 снимков на класс,
balanced accuracy≥0.90 и recall каждого класса≥0.85. Он не заменяет приёмку
интерфейса, ошибок ввода, скорости, памяти и воспроизводимости.

Если результаты низкие, сначала разберите ошибки на val и обучающей части:
разметку, разнообразие, ракурсы, фон, масштаб телефона. После знакомства с
ошибками test и доработки по ним старый test становится набором разработки;
для честной итоговой приёмки нужен новый независимый набор.

## 9 Передайте систему другой группе

Передайте код и инструкции, `models/base`, папку выбранного run, конфигурацию,
разметку/разбиение и согласованный набор данных. `.venv` не передавайте.
На другом ПК установите зависимости, выполните doctor, predict, batch и benchmark.
Проверьте минимум пять корректных фотографий и ошибки ввода без устных подсказок.
Зафиксируйте результат в протоколе. Исходные метрики качества пока неизвестны.
