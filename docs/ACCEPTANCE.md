# Итоговые испытания

Эта инструкция применяется после обучения на реальных данных. В стартовой
версии ни один целевой показатель качества на телефонах не объявляется достигнутым.

## Фиксация версии

Сохраните run.json, config_snapshot.json, dataset_snapshot.csv, хеш базы,
версию кода, дату, Python/библиотеки и описание ПК. Не меняйте test, порог,
предобработку или веса после фиксации без выпуска новой версии.

## Качество

Команда evaluate со split test формирует metrics.json и predictions.csv.
Требуются минимум 100 снимков каждого класса, balanced accuracy≥0.90,
recall каждого класса≥0.85. Все корректные входы должны технически обработаться.
Кэшированная оценка головы подтверждает метрики на зафиксированных признаках;
полный путь чтения фотографий дополнительно проверяется benchmark и batch.

Отдельно укажите число физических устройств и моделей, пересечение моделей
между train/test, ограничения источников, условия и ракурсы съёмки. Дополнительно
полезна оценка на моделях устройств, отсутствовавших в train. Малый размер
набора означает статистическую неопределённость; точечная метрика не гарантирует
качество на всех будущих телефонах.

## Скорость и память

```bash
python -m phone_vlm benchmark --run runs/experiment_001 --device cpu --limit 100 --output reports/benchmark_001
```

Модель загружается один раз, выполняется прогрев, затем обрабатываются первые
100 test-кадров в порядке CSV. Не менее 95 должны успешно обработаться за≤2 с.
Замер охватывает чтение, предобработку, энкодер и голову; запись журнала, GUI,
загрузка модели и вывод консоли не включены. Укажите это в протоколе.

RSS процесса снимается каждые 10 мс от начала загрузки модели. Отчёт содержит
наблюдаемый пик и прирост. Краткий пик между отсчётами может быть пропущен,
VRAM этим способом не измеряется. Для строгой приёмки дополнительно проверьте
процесс системным монитором и согласуйте трактовку лимита 2 ГБ. Укажите точный CPU,
ОЗУ, ОС, число потоков и состояние питания ноутбука. Контейнерный тест не заменяет этот ПК.

## Интерфейс и устойчивость

На новом окружении по инструкции выполните минимум пять распознаваний, затем
20 за один сеанс GUI. Проверьте окно при 1366×768, сохранность пропорций
превью, русские сообщения, совпадение записей журнала с результатами и версиями.
Отключите сеть и повторите распознавание.

Проверьте отсутствующий путь, TXT, повреждённый JPEG, слишком маленький и слишком
большой кадр. После каждой ошибки в GUI можно выбрать другой файл; в batch
ошибка не останавливает соседние строки. Для граничных размеров используйте
отдельные технические изображения, не добавляя их в тест качества телефонов.

Обработка чёрного/белого кадра даёт предупреждение. Она не должна преподноситься
как надёжное обнаружение отсутствия телефона. Проверку порога можно отдельно
воспроизвести на технических данных, а реальные примеры низкой уверенности
подбираются по val, без изменения зафиксированного test.

## Шаблон протокола

Заполните `reports/acceptance_template.csv`; пустые поля — ещё не результаты.
Укажите комплектность, запуск на другом ПК, качество, размер фактической
поставки/установки, скорость, память, журнал, некорректный ввод и ограничения.
При несоответствии запишите причину и план проверки новой версии.
